# 인식 PoC 계획 — WBA

상태: 초안 v1 · 2026-10-19 · 기간: 파트타임 4–6주 · 위치: `poc/` (Python, 앱과 분리)

## 1. 답해야 할 질문

> 스캔한 찬양 악보를 처음부터 직접 입력하는 것보다 적은 수고로 **인식, 수정, 전조, 재렌더링**할 수 있는가? 그렇다면 페이지당 정확도와 비용은 얼마인가?

결정이 따로 필요한 하위 질문 두 개:
- **Q1 (코드, 모드 ①/②):** 기존 OCR + 문법 파이프라인에 비전 LLM 단계를 더하면, 비용을 정당화할 만큼 코드, 섹션, 제목 정확도가 올라가는가?
- **Q2 (전체 악보, 모드 ③):** OMR 엔진 하나 또는 하이브리드가 §5의 모드 ③ 기준을 넘을 수 있는가?

## 2. 테스트 코퍼스

| 세트 | 페이지 | 설명 | 정답 데이터 |
|---|---|---|---|
| **KR-PDF** | 20 | 한국 CCM 리드시트, 디지털 PDF (멜로디 + 코드 + 한글 가사, 1–2절) | 10장은 전체 MusicXML. 20장 모두 코드, 섹션, 키 |
| **EN-PDF** | 20 | 영어 찬양 리드시트 (SongSelect 스타일) | 10장은 전체 MusicXML. 20장 모두 코드, 섹션, 키 |
| **CHART** | 10 | 가사 위 코드 악보 (오선 없음), 한/영 | 코드, 섹션, 키 |
| **PHOTO** | 15 | 위 인쇄 페이지 중 15장을 휴대폰으로 촬영: 평평하고 밝게 5장, 비스듬히 5장, 어둡거나 휘어진 상태 5장 | 원본 페이지의 정답을 그대로 사용 |
| **HARD** | 5 | 피아노/보컬 2단 오선, D.S./Coda, 손으로 고친 코드 | 코드 + 키만 (도전 과제) |

합계: **70페이지, 그중 약 20페이지는 음표 단위 정답 데이터.**

- **저작권:** 팀이나 교회가 이미 라이선스를 가진 악보만 사용. 코퍼스는 비공개 버킷에 두고 git에 절대 커밋하지 않음. 허용되는 경우에만 파일 해시와 직접 채보한 정답 데이터를 커밋.
- 음표 정답은 MuseScore로 입력해 MusicXML로 내보냄. 코드, 섹션, 키 정답은 JSON 스키마(`poc/truth/<page>.json`)로 저장.
- 전체 채보는 페이지당 약 20분, 총 6–7시간 예상. 이 시간이 곧 §5의 **직접 입력 기준선**이 됨.

## 3. 시험할 접근법

| ID | 파이프라인 | 대상 |
|---|---|---|
| **A** | 현재 앱 파이프라인 (Google Vision + `chordPattern`/`buildSongFromOcr`), Node CLI 래퍼로 실행 | 코드, 섹션, 가사 |
| **B** | 비전 LLM 단독: 페이지 이미지 → JSON (코드+bbox, 섹션, 키, 박자, 제목), 그리고 별도로 → MusicXML | 전부 ("LLM만으로 되나?"의 기준선) |
| **C** | A + 비전 LLM 모호성 해소: LLM이 이미지 + ID가 붙은 OCR 토큰을 받아, 토큰 ID를 참조하는 라벨과 수정안을 돌려줌 | 코드, 섹션, 제목 |
| **D1** | homr (수정 없음) | 음표, 키, 박자 |
| **D2** | Audiveris (수정 없음, CLI 일괄 처리 → MusicXML + .omr) | 음표, 키, 박자, 일부 텍스트 |
| **D3** | oemer | 음표, 키, 박자 |
| **E** | 하이브리드: D 중 최고 + C를 ScoreIR로 병합 + 규칙 검증 (AI_RECOGNITION_RESEARCH §4) | 전부 |

LLM 모델: 서로 다른 제공자의 최신 비전 모델 최소 2개(예: Claude Sonnet 5.5 / Opus 5.5와 경쟁 모델 하나). Temperature 0, 고정된 프롬프트 버전을 결과에 저장.

전처리 변형(PHOTO 세트에 적용): 없음 / 기울기 + 원근 보정(OpenCV) / + 적응형 이진화 + 업스케일.

|---|---|---|
| **E1 코드** | 모든 세트에서 A vs B vs C | 코드 F1, 섹션 F1, 제목/키 정확도, 페이지당 비용, 지연 시간 |
| **E2 기보** | 정답이 완전한 20페이지 + 그 사진들에서 D1/D2/D3/B(MusicXML) | 음높이, 리듬, 키, 박자, 마디 정확도 |
| **E3 하이브리드 + 검증** | 같은 페이지에서 E 실행. 검증기가 오류를 얼마나 **표시**하는지(오류 재현율), 맞는 항목을 얼마나 잘못 표시하는지(오경보율) 측정 | 표시 정밀도/재현율, 표시되지 않고 남은 오류 비율 |

| **E5 수정 시간** | 최소한의 검토 프로토타입(웹 페이지: 원본 + 인식 결과 오버레이 + 표시 항목 목록, 음표 수정은 MuseScore). 테스터 3명(인도자 1, 연주자 2)이 각 6페이지 수정. 절반은 최고 파이프라인 결과에서, 절반은 처음부터 입력 | 페이지당 수정 시간 중앙값, 인식 vs. 직접 입력 |

## 5. 지표와 통과 기준

채점 전 정규화:
- 코드: 표준 형태로 통일(`CM7` ≡ `Cmaj7` ≡ `CΔ7`, `C-7` ≡ `Cm7`). 이명동음은 같다고 보지 **않음**(표기가 중요하므로).
- 음표는 마디 단위로 시퀀스 정렬해서 비교(music21 기반 diff나 OMR-NED 편집 거리 같은 표준 OMR 평가 방식).

| 지표 | 정의 | Q1 통과 (모드 ①/② LLM 단계) | Q2 통과 (모드 ③) |
|---|---|---|---|
| 코드 F1 | 같은 줄/마디 안의 토큰 일치, 정규화 | C ≥ A + 3 포인트 **그리고** PDF ≥ 0.95 / PHOTO ≥ 0.90 | ≥ 0.95 / ≥ 0.90 |
| 섹션 F1 | 라벨 + 시작 위치(±1줄 또는 마디) | ≥ 0.90 | ≥ 0.90 |
| 키 정확도 | 페이지 단위 정확 일치 | ≥ 0.95 (코드 기반) | ≥ 0.98 (조표) |
| 박자표 정확도 | 페이지 단위 정확 일치 | — | ≥ 0.98 |
| 음높이 정확도 | 정렬된 음표 중 step+alter+octave가 맞은 비율 | — | PDF ≥ 0.95 / PHOTO ≥ 0.90 |
| 리듬 정확도 | 정렬된 음표 중 길이가 맞은 비율 | — | ≥ 0.92 |
| 마디 정확도 | 오류가 하나도 없는 마디 비율 | — | PDF ≥ 0.85 |
| 미표시 오류 비율 | 검증기가 표시하지 **못한** 오류 ÷ 전체 요소 | — | ≤ 2% |
| 수정 시간 | 페이지당 분 단위 중앙값 vs. 직접 입력 | 페이지당 2분 미만 | **직접 입력의 50% 이하** |
| 비용 | 페이지당 API + 연산 | ≤ $0.03 | ≤ $0.15 |
| 지연 시간 | 페이지당 p95 | ≤ 10초 | ≤ 60초 |

판정 규칙:
- **Q1 진행:** C가 해당 기준을 충족 → 1단계에서 LLM 라벨 단계 출시. 아니면 A를 유지하고 구체적인 실패 유형만 고침.
- **Q2 진행:** 하이브리드가 **PDF에서 수정 시간 + 미표시 오류 비율 + 마디 정확도**를 충족 → 3단계 전체 개발.
- **Q2 부분 진행:** PDF는 통과, PHOTO는 실패 → 모드 ③은 PDF에만 제공하고, 사진에는 "코드만"으로 표시.
- **Q2 중단:** → 3단계를 MusicXML 가져오기 + 전조로 축소(로드맵 참고)하고, 상용 OMR 라이선스 검토.

비용 목표는 임시값이며, PoC 시작 시점에 실제 제공자 가격으로 갱신해야 합니다.

## 6. 실험 환경

```
poc/
  corpus/         (git 제외. 비공개 버킷에서 동기화)
  truth/          페이지 JSON + MusicXML 정답
  pipelines/      a_ocr_grammar/ (node로 앱 코드 호출), b_llm/, c_hybrid_chords/,
                  d_homr/ d_audiveris/ d_oemer/ (각각 Docker 이미지, 엔진 수정 없음), e_hybrid/
  eval/           normalize.py, score_chords.py, score_notes.py (music21), report.py
  results/<run-id>/  원본 출력 + metrics.json + cost.json (+ 프롬프트와 모델 버전)
```
- 모든 실행은 `run-id`(코퍼스 해시, 파이프라인 버전, 모델 ID, 프롬프트 해시)로 재현 가능.
- Python 3.12 venv. 엔진은 각자의 컨테이너에서 실행(AGPL 격리, 의존성 충돌 방지).
- `report.py`가 실행마다 마크다운/HTML 비교 표 하나를 생성.

## 8. 결과물

1. `poc/REPORT.md`: 접근법별·세트별 지표 표, 예시가 포함된 실패 유형 분류, 비용과 지연 시간, Q1/Q2 결정.
2. 재사용 가능한 평가 환경 (이후 모델이나 엔진을 업그레이드할 때 회귀 테스트로 계속 사용).
3. music21로 검증한 TS 전조 프로토타입 (로드맵 1.1과 3.2의 바탕).
4. 실제로 권장하는 엔진별 라이선스 메모.
