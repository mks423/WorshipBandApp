## 1. 현재 상태 (이 저장소 점검 결과, 커밋 `b08a9bd`)

TypeScript 약 5,400줄, Expo SDK 57 / RN 0.86, 단위 테스트 75개 통과.

| 영역 | 현재 구현 | 판단 |
|---|---|---|
| `chord-scan/` | Google Vision OCR 어댑터, 토큰→줄 묶기, 코드 문법(`chordPattern.ts`, 엄격하고 테스트가 잘 되어 있음), 붙은/합쳐진 토큰 복구, 코드↔가사 정렬, 숨겨진 WebView의 pdf.js로 PDF 래스터화 | **유지.** 모드 ①, ② 인식의 핵심. 제공자 어댑터 구조(`ocrProviders/`)가 이미 특정 제공자에 묶여 있지 않음. |
| `transpose/` | 반음 기반 코드 전조 | **코어 재작성.** 목표 키에 맞는 표기가 틀림(G→F에서 `A#`, G→Ab에서 `G#`, `C#`, `D#`). 음정과 키를 인식하는 방식이어야 함. 테스트와 API 형태는 유지 가능. |
| `types/song.ts` | Song → Section → Line → Segment(chord, lyric, confidence, chordPosition) | **개념 유지.** 원본 위치가 연결된 코드 악보 중간 표현(IR)이며, 스펙이 요구하는 바로 그것. 더 큰 모델 안의 `ChordChartDoc`이 됨(DATA_MODEL 참고). |
| `library/`, `setlist/` | AsyncStorage JSON 덩어리(저장할 때마다 라이브러리 전체를 다시 씀), 이미지는 문서 폴더나 IndexedDB | **저장소를 SQLite로 교체.** 통째로 다시 쓰는 방식은 곡 2,000개를 감당하지 못하고 동기화도 불가능. |
| `song-form/` 화면 | 오버레이 편집기(735줄), 키 변경, 내보내기, 섹션 마커, 메모 | **동작은 유지하고 리팩터링.** 제스처와 오버레이 로직을 분리하고 디자인 토큰으로 스타일 재적용. |
| `App.tsx` | 상태 머신으로 직접 만든 내비게이션 | expo-router로 **교체**(탭 + 스택, iPad 분할 화면). |
| `design-system/` | 목업에서 뽑은 토큰, 아직 미적용 | 내비게이션 개편 때 **적용**. |
| 보안 | `EXPO_PUBLIC_GOOGLE_VISION_API_KEY`가 번들에 포함, URL 쿼리 파라미터로 전송 | 공개 빌드 전에 **반드시 수정**: 서버 프록시를 거치도록. |

결론: **처음부터 다시 만들지 말고 이 저장소를 발전시킨다.** 힘들게 다듬은 OCR 휴리스틱(빽빽한 코드 줄, OCR 오인식, 한국어 가사)이 여기서 가장 가치 있는 코드입니다.

## 3. 주요 데이터 흐름

### 3.1 가져오기 (오프라인 가능)
1. 파일 선택 → SHA-256 계산 → `originals/<sha>.<ext>`에 복사(변경 불가) → `score_assets` 행 추가.
2. PDF: 페이지 수 확인 → 필요할 때 pdf.js로 각 페이지를 2배 해상도로 `pages/<sha>/<n>.png`에 래스터화(언제든 다시 만들 수 있는 캐시). 이미지: 한 페이지.
3. 곡이 바로 라이브러리에 나타나고, 인식을 돌리기 전에도 읽을 수 있음.

### 3.2 인식 (모드 ①/②, 현재 파이프라인)
1. 사용자가 "코드 인식"을 누름. 페이지 래스터를 `POST /ocr`(Edge Function → Google Vision)로 보내거나, 오프라인이면 outbox 대기열에 넣음.
2. 기기에서: 기존 `buildSongFromOcr` → `ChordChartDoc` 초안. 모든 요소에 `{page, bbox, confidence, provenance:'ocr'}`가 붙음.
3. 선택적으로 `POST /recognize/labels`(비전 LLM): 페이지 이미지 + OCR 토큰을 받아서 제목, 키, 섹션 라벨을 **토큰 ID 참조로** 돌려주고, 신뢰도 낮은 토큰의 수정 제안을 줌. LLM은 페이지의 박스를 가리키지 않는 코드를 추가할 수 없음.
4. 검토 UI → 사용자 확인 → `reviewed_at` 설정. 초안이 편곡의 코드 악보가 됨.

### 3.3 인식 (모드 ③, PoC 후 조건부)
`원본 업로드 → recognition_job(queued) → 워커: 전처리 → OMR + OCR + LLM 병렬 → 병합 → 검증 → ScoreIR + 표시 항목 → 앱에서 나란히 비교 검토 → 사용자 수정 → MusicXML v1 (변경 불가) → 렌더링`

### 3.4 전조
`arrangement.key` 변경 → `transpose(doc, fromKey, toKey)`는 순수 함수 → 다시 렌더링. 원본 문서는 절대 바뀌지 않음. 연주 버전은 `{key, capo}`를 저장하고, 전조 결과는 필요할 때 다시 생성(결정적)하며 렌더 캐시는 선택.

### 3.5 라이브 연주
송폼 → 뷰어가 다음 곡 페이지를 미리 로드 → 페달이나 키보드 이벤트 → 페이지 넘김. 네트워크 호출이 없으므로 비행기 모드에서도 동작.

## 6. 백엔드 (5단계 이후, 지금 설계)

- **Supabase**: `church_id` 기준 RLS가 적용된 Postgres, Auth(이메일 매직 링크, Apple, Google, Kakao), 원본과 파생 파일용 Storage. 전송 비용이 커지면 Cloudflare R2로 이전. 저장 키가 콘텐츠 주소 방식이라 이전은 복사만 하면 됨.
- **Edge Functions**가 앱이 유료 API에 닿는 유일한 경로. 인증, 사용량 한도, 사용량 측정을 강제.
- **대기열**: 처음에는 Supabase Queues(pgmq), 워커가 폴링. 실제로 필요해질 때까지 Redis나 Celery는 추가하지 않음.
- **워커**: Python 3.12 컨테이너(Fly.io / Cloud Run / Railway), CPU 우선. PoC 지연 시간상 필요할 때만 GPU. 엔진마다 이미지 하나(라이선스 때문에 OMR 엔진 격리).
- **동기화**: 기기의 커맨드 outbox → 서버가 RLS로 적용 → 커서 이후 변경분을 내려받음. 충돌 정책: 메타데이터는 필드 단위로 마지막 작성자가 이김. 편곡과 흐름은 버전 관리(충돌 시 분기 버전을 만들고 사용자가 선택). 개인 필기는 충돌하지 않음.

## 8. 가장 어려운 기술 문제 (순위)

1. **실제 입력에서 음표 단위 인식 정확도**(휴대폰 사진, 한국 CCM 레이아웃, 오선 아래 두 언어 가사). 오픈소스 중 아직 신뢰할 만한 것이 없음. 모드 ③을 조건부로 둔 이유.
2. **다시 타이핑하는 것보다 빠른 수정 UX.** 인식된 악보를 고치는 데 직접 입력보다 오래 걸리면 기능의 가치가 없음. 그래서 PoC 지표에 "수정 시간 vs. 직접 입력 시간"이 있음.
3. **모든 요소를 원본 위치에 연결하기.** OMR 엔진이 내놓는 MusicXML에는 좌표가 부실하거나 없음. 음표마다 박스를 얻으려면 엔진 내부 데이터(Audiveris의 `.omr`, homr의 검출 결과)를 쓰거나 사후에 다시 맞춰야 함.
4. **버전이 있는 팀 편곡의 오프라인 우선 동기화.** 원래 어려운 문제. 대부분의 엔티티에 작성자를 한 명만 두고 나머지는 버전 관리해서 단순하게 유지.
5. **라이브 안정성**: 페달, 페이지 넘김 지연, 긴 송폼에서 WebView 메모리 압박 피하기.
