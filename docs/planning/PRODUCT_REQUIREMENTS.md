## 1. 문제

한국과 미국의 찬양팀은 악보를 PDF, 사진, 출력물로 받는데, 키는 출판사가 정한 그대로입니다. 인도자는 매주 곡마다 키와 섹션 순서를 정하고, 그걸 연주자들에게 전달해야 합니다. 지금은 이 과정이 전부 수작업입니다. 코드 악보를 다시 타이핑하고, PDF 위에 새 코드를 손으로 적고, 단톡방에 "V1 C V2 C C B C" 같은 메시지를 돌립니다.

forScore는 태블릿에서 악보를 *읽고 정리하는* 문제를 해결했습니다. 하지만 음악 내용은 이해하지 못합니다. 스캔한 악보를 전조할 수 없고, 팀 편곡이라는 개념도 없습니다.

## 2. 제품 방향

**가져오기 → 인식 → 검토 → 전조 → 편곡 → 공유.** 절대 어기지 않는 원칙이 하나 있습니다. *앱은 음악을 몰래 바꾸지 않는다.* 인식된 모든 기호는 원본 페이지의 해당 위치에 연결됩니다. 시스템이 확신하지 못하는 부분은 반드시 사람이 검토합니다.

## 3. 사용자

| 페르소나 | 주요 작업 | 기기 |
|---|---|---|
| **인도자** (주 구매자, 도입을 이끄는 사람) | 곡과 키를 고르고, 송폼을 만들고, 주간 셋을 배포 | 주중에는 휴대폰, 무대에서는 iPad |
| **연주자** (건반, 기타, 베이스, 드럼, 보컬) | 이번 주 셋을 맞는 키로 열고, 연주 중 흐름을 따라감 | 보면대 위 iPad 또는 휴대폰, 블루투스 페달을 같이 쓰는 경우가 많음 |
| **교회 관리자** | 멤버, 결제, 공용 라이브러리 관리 | 휴대폰 또는 PC |
| **뷰어** (음향·미디어팀, 대타 연주자) | 셋과 편곡을 열람 | 휴대폰 |

대상 시장: 한국(한국 CCM, 한글 가사가 들어간 리드시트)과 미국(CCLI/SongSelect 스타일 리드시트와 코드 악보). UI는 처음부터 영어와 한국어로 모두 제공해야 합니다.

## 4. 세 가지 "전조" (절대 섞어서 다루지 않음)

제품은 UI와 코드 모두에서 이 셋을 분리해야 합니다. 각각 다른 라벨이 붙은 결과를 만듭니다.

| 모드 | 입력 | 바뀌는 것 | 정확도 | 상태 |
|---|---|---|---|---|
| **① 코드 오버레이** | 스캔한 모든 페이지(PDF/사진) | 코드 *라벨*만 바뀝니다. 원래 코드를 가리고 그 자리에 전조된 텍스트를 그립니다. 오선 악보는 **바뀌지 않습니다.** | 코드는 정확함. 오선의 음표는 원래 키 그대로 | **현재 구현됨** (`SourceOverlayScreen`) |
| **② 코드 악보** | 인식된 코드·가사 구조(섹션, 줄, 가사 단어 위의 코드) | 원하는 키로 코드 악보를 새로 조판 | 검토를 마치면 정확함 | 데이터 모델은 있음(`Song.sections`). 깔끔한 렌더러는 아직 없음 |
| **③ 재구성 악보** | OMR + 비전 인식 → 검토된 MusicXML | 조표, 모든 음표, 임시표, 코드 심볼, 슬래시 베이스를 바꾼 뒤 악보를 다시 그림 | 인식 품질과 검토 품질만큼 정확함 | **연구 / PoC** |

UI 요구사항: 모드 ①로 보는 페이지에 오선 악보가 있으면 "코드만 전조됨 · 오선 악보는 원조"(영어: "Chords transposed · notation in original key") 배지를 계속 표시해야 합니다. 멜로디를 보는 연주자가 절대 오해하지 않아야 합니다.

## 5. MVP 범위

MVP는 **모드 ①과 ②, 라이브러리와 뷰어, 송폼(셋리스트), Song Flow이며, 모두 기기에서 오프라인으로 iPad와 휴대폰에서 동작**합니다. 모드 ③은 별도 PoC로 병행하고([POC_PLAN](POC_PLAN.md) 참고), 통과 기준을 넘을 때만 제품에 넣습니다.

### 5.1 MVP에 포함

**A. 라이브러리와 뷰어**
- A-1 파일 앱, 사진, 카메라에서 PDF, JPG, PNG 가져오기. 여러 페이지 PDF는 라이브러리 항목 하나로 묶음(구현됨).
- A-2 원본은 바이트 단위로 그대로 저장(콘텐츠 해시). 나머지는 모두 원본에서 파생.
- A-3 라이브러리 메타데이터: 제목, 아티스트, 원래 키, BPM, 박자, 태그, 분류. "D키 곡 전부" 같은 검색과 필터 지원.
- A-4 전체 화면 뷰어: 핀치 줌, 스와이프나 탭 영역으로 페이지 넘김, 세로/가로 모드, iPad 가로 모드에서 두 페이지 펼쳐 보기.
- A-5 블루투스 페이지 넘김 페달. 페달은 키보드로 인식되며(방향키, PageUp/PageDown, 스페이스), 두 가지 페달 모드를 모두 지원해야 함.
- A-6 페이지 위 필기: 펜, 형광펜, 지우개, 텍스트 메모. 애플펜슬과 손가락 입력 지원. 필기는 페이지 기준 정규화 좌표의 벡터 레이어로 저장하고 원본에 절대 합치지 않음.
- A-7 페이지별 북마크.
- A-8 가져온 뒤에는 모든 기능이 오프라인으로 동작.

**B. 인식 (모드 ①, ②)**
- B-1 스캔 페이지에서 코드와 가사 인식(구현됨: Google Vision OCR + 코드 문법).
- B-2 섹션 라벨 인식: Intro, Verse, Chorus, Bridge, Ending과 한국어 라벨 전주, 후렴, 간주, 브릿지, 엔딩.
- B-3 제목과 키 인식. 키 판별은 "첫 코드"보다 나은 방식이어야 함(로드맵 1.2 참고).
- B-4 검토 UI: 인식된 코드를 탭해서 수정, 신뢰도 낮은 항목 강조, 코드와 섹션 추가·삭제(기본 형태로 구현됨).
- B-5 인식 결과를 몰래 확정하지 않음. 사용자가 페이지를 검토 완료로 표시하기 전까지 결과는 *초안*.

**C. 전조 (모드 ①, ②)**
- C-1 목표 키에 맞는 이명동음 표기로 전조(G→F에서 A♯가 아니라 B♭). 현재 구현은 이걸 틀리게 하고 있으며, 로드맵 1.1에서 고침.
- C-2 슬래시 코드, 텐션, 변화음이 정확하게 유지됨.
- C-3 기타용 카포 표시(코드 모양 키 + 카포 프렛).
- C-4 곡 하나에 여러 키(예: 남자 키, 여자 키)를 두되 원본을 복제하지 않음.

**E. Song Flow**
- E-1 섹션이 블록이 됨(Intro, V1, C, V2, C×2, B, Ending). 추가, 삭제, 복제, 드래그로 순서 변경, 반복, 건너뛰기 가능.
- E-2 블록마다 마디 수와 밴드 지시사항. 자유 입력과 프리셋("피아노만", "4마디 후 드럼 시작", "풀 밴드", "빌드업", "조용히 엔딩", "인도자 큐" 등).
- E-3 섹션을 페이지 영역(모드 ①, 기존 섹션 마커 사용) 또는 마디 범위(모드 ③, 이후)에 연결.
- E-4 곡마다 이름 붙인 편곡 여러 개(예: "주일 1부 풀 밴드", "어쿠스틱").
- E-5 **연주용 개요 화면**: 전체 흐름을 한 화면에 보여주고, 보면대 거리에서도 읽힘.
- E-6 흐름을 이미지나 텍스트로 내보내기/공유(곡 단위는 구현됨, 흐름으로 확장).

**송폼(셋리스트)**
- S-1 라이브러리 곡으로 송폼 만들기. 항목마다 편곡, 키, 메모를 따로 가짐.
- S-2 송폼 재생: 뷰어가 곡 순서대로 넘어가고, 페달로 곡 경계도 넘어감.

### 5.2 MVP에서 제외 (이후 단계)

| 기능 | 단계 | 미루는 이유 |
|---|---|---|

| 모드 ③ 재구성 악보의 정식 기능화 | 3 (조건부) | PoC 통과가 전제 |
| 버전 히스토리 UI | 5 | 변경 기록은 1단계부터 쌓고, UI는 나중에 |
| 대화형 AI 어시스턴트 | 6 | 1단계에서 커맨드 레이어를 만들어 두므로 나중에 붙이기 쉬움 |
| 구독, 결제, 사용량 한도 | 6 | |
| 오디오 재생, 클릭 트랙, MIDI | — | 범위 밖 |
| 공개 곡 카탈로그 / 커뮤니티 공유 | — | **저작권 위험**(§8 참고). 계획 없음. |

## 6. 주요 내비게이션

`라이브러리 · 송폼 · 뷰어 · Song Flow · 팀`

- 휴대폰: 하단 탭 바. 뷰어는 탭이 아니라 곡이나 송폼에서 들어가므로, 탭 4개 + "지금 연주 중" 진입점.
- iPad: 사이드바 + 콘텐츠 영역. 뷰어는 전체 화면이며 메뉴는 자동으로 숨겨짐.
- "팀"은 MVP에서 자리만 둠("준비 중" + 기기 내 내보내기/공유).
- AI 기능은 상황에 맞게 등장함(예: 페이지에서 "코드 인식", Song Flow에서 "섹션 감지"). MVP에 별도 채팅 탭은 없음.

## 7. UX 원칙

1. **무대 화면은 건드리지 않는다.** 뷰어에서는 팝업, 토스트, 네트워크 로딩 표시가 없음. 큰 글씨, 높은 대비, 어두운 "무대" 팔레트(`src/design-system/colors.ts`에 토큰 있음).
2. **원본은 언제나 탭 한 번 거리에.** 모든 파생 화면에 "원본 보기" 토글.
3. **불확실성은 숨기지 않고 보여준다.** 신뢰도 낮은 항목은 일관된 주황색 밑줄, 페이지 헤더에 검토 필요 개수 표시.
4. 읽기는 **태블릿 우선**, 계획은 **휴대폰 우선**.
5. 장식용 카드, 그라데이션, 그림자 없음. 위계는 타이포그래피와 여백으로 표현. 기존 디자인 토큰(Pretendard, 따뜻한 종이 팔레트) 사용.
6. 파괴적인 동작은 모두 되돌릴 수 있고, 원본은 절대 수정하지 않음.

## 8. 비기능 요구사항

| 영역 | 요구사항 |
|---|---|
| 성능 | 캐시된 페이지 넘김 100 ms 미만. 10페이지 PDF 첫 열기 1.5초 미만(2020년 이후 iPad 기준). 곡 2,000개 라이브러리가 60 fps로 스크롤. |
| 오프라인 | 인식(클라우드 OCR)을 제외한 모든 MVP 기능이 네트워크 없이 동작. 인식 요청은 다시 온라인이 될 때까지 대기열에 보관. |
| 안정성 | 앱이 죽어도 데이터 손실 없음. 쓰기는 트랜잭션 단위(SQLite). |
| 개인정보·보안 | 앱 번들에 API 키 없음(현재 Vision 키가 번들에 **들어 있음**, 로드맵 1.6 참고). 업로드한 악보는 본인만, 이후에는 본인 교회만 볼 수 있음. |
| 현지화 | 모든 UI 문구 한/영 제공. 섹션 라벨은 두 언어 모두 인식. |
| 접근성 | 뷰어 외 화면은 동적 글자 크기 지원, 터치 영역 최소 44 pt, 컨트롤에 VoiceOver 라벨. |
| 저작권 | 앱은 사용자나 교회가 올린 파일을 저장할 뿐 공개 배포하지 않음. 팀에 공유할 때 CCLI/라이선스 안내 표시(5단계). |

## 9. 성공 지표 (MVP)

- 일반적인 2페이지 리드시트 기준으로, 인도자가 PDF 가져오기, 코드 수정, 전조, 흐름 만들기, 공유까지 **5분 안에** 끝냄.
- 테스트 세트에서 코드 인식 정확도가 [POC_PLAN](POC_PLAN.md) §5의 목표를 달성.
- 전조 골든 테스트(코드 코퍼스 전체 × 12×12 키 조합)에서 표기 정확도 **100%**.
- 시범 찬양팀 10곳(한국 5, 미국 5)이 4주 연속 주일에 사용.

## 10. 열린 질문

1. 웹을 정식 제품으로 낼지, 개발 편의용으로만 둘지? (웹은 지금 동작함. 이 문서는 개발용으로 가정.)
2. 요금 모델은 교회 단위인가, 사용자(좌석) 단위인가? 6단계의 사용량 한도 설계에 영향.
3. 한국 팀에 숫자 코드(내슈빌 넘버) 표시 모드가 필요한가? 전조를 음정 기반으로 바꾸면 쉽게 추가할 수 있음. 빠른 후속 기능으로 권장.
