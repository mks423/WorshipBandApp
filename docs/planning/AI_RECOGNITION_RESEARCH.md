## 1. 무엇을 인식해야 하고, 각각 얼마나 어려운가

| 대상 | 일반적인 위치 | 난이도 | 적합한 기법 |
|---|---|---|---|
| 제목, 아티스트, ©/CCLI 줄 | 상단의 인쇄 텍스트 | 쉬움 | OCR + 레이아웃 휴리스틱, 또는 비전 LLM |
| 코드 심볼 (슬래시, 텐션, 변화음 포함) | 오선이나 가사 위의 텍스트 | 중간. 빽빽한 줄, OCR 혼동(`B`/`8`, `G`/`6`, `m`/`rn`), 위첨자 | OCR + 엄격한 문법(**이미 구현됨**) + 애매한 토큰은 비전 LLM |
| 섹션 라벨 (V1, Chorus, 후렴, 간주, D.S.) | 텍스트, 박스나 굵은 글씨인 경우가 많음 | 쉬움–중간 | OCR + 사전 + 비전 LLM |
| 가사 (한/영, 여러 절이 겹쳐 있음) | 오선 아래 텍스트 | 중간. 절 겹침과 하이픈 | OCR + 줄 묶기. 음절과 음표를 맞추려면 OMR이 필요 |
| 조표 | 오선 시작 부분의 기호 | OMR은 중간, LLM은 신뢰하기 어려움 | OMR + 코드 근음으로 교차 확인 |
| 박자표 | 기호 | 쉬움–중간 | OMR + 음표 길이 합 검증 |
| 음표, 쉼표, 길이, 임시표, 붙임줄, 빔 | 오선 기보 | **어려움**. 작은 기호, 사진 잡음, 빔 | **전용 OMR만 가능** |
| 마디선, 반복, 볼타, D.S./D.C./Coda | 기호 + 텍스트 | 중간–어려움 | OMR(기호) + OCR(텍스트 표시) |

핵심 통찰: **찬양팀에게 가치의 약 80%는 위 네 줄에 있고**, 이는 대부분 기존 파이프라인이 이미 처리하는 텍스트 문제입니다. 음표 단위 OMR은 비싸고 위험한 나머지 20%입니다.

## 2. 접근법 비교

### A. OCR + 코드 문법 (현재 구현)
- **방식:** Google Vision 단어 박스 → 줄 묶기 → 엄격한 코드 정규식 → 코드/가사 짝짓기.
- **장점:** 싸고, 결정적이고, 토큰마다 박스가 공짜로 따라오고, 한국어를 처리하며, 실제 악보로 이미 다듬어져 있음(붙은 토큰 분리, 오인식 복구).
- **한계:** 오선 기보를 이해하지 못함. 위첨자나 겹쳐 쓴 텐션, 오선 영역 안의 코드, 손으로 쓴 코드. 섹션 인식이 사전 기반.
- **비용:** 낮음(페이지당 OCR 호출 1회).

### B. 범용 비전 LLM 단독 (이미지 → 구조화 JSON / MusicXML)
- **방식:** 페이지 이미지를 보내고 코드, 섹션, 가능하면 음표까지 요청.
- **장점:** 레이아웃과 의미 파악에 뛰어남(어느 텍스트가 제목인지, "2x"나 "To Coda"가 무슨 뜻인지). 낯선 형식에도 강하고, 두 언어 텍스트를 잘 읽음.
- **한계 (중요):**
  - **음표 단위 채보는 신뢰할 수 없음.** 공개된 OMR 평가와 실무자 보고에서 최신 VLM도 음표를 빠뜨리거나 지어내고, 덧줄 수를 잘못 세고, 길이가 틀린 마디를 만든다는 결과가 일관되게 나옴. PoC E2에서 측정하기 전까지는 검증되지 않은 것으로 취급.
  - **좌표를 믿을 수 없음.** LLM이 주는 박스는 대략적임*(모델별 확인 필요)*. 그래서 "모든 요소를 원본 위치에 연결"을 LLM 출력만으로는 할 수 없음.
  - **환각 위험.** 예상되는 코드 진행을 모델이 "채워 넣을" 수 있음. "지어내지 않는다" 원칙과 충돌.
  - 비결정적 출력, 페이지당 비용, 모델 변경에 따른 결과 변동.
- **판단:** **구조 파악과 모호성 해소**에 쓰되, OCR/OMR 검출 결과를 참조하도록 제한. 음악 기호의 유일한 출처로는 절대 쓰지 않음.

### C. 전용 OMR 엔진

| 엔진 | 기술 | 라이선스 | 강한 입력 | 출력 | 상태 |
|---|---|---|---|---|---|
| **Audiveris** | 고전 CV + NN 분류기, Java | AGPL-3.0 | 깨끗한 인쇄 PDF, 여러 단 오선, 총보에 강함 | MusicXML 4.0 + 기호 위치가 담긴 상세 `.omr` 프로젝트 | 성숙, 활발함(5.10.x, 2026) |
| **homr** | 분할 + 트랜스포머(oemer의 오선 검출 + TrOMR 방식 디코더 기반) | AGPL-3.0 | **카메라 사진**, 단일 오선/단순 레이아웃 | MusicXML (음높이 + 리듬. 셈여림, 아티큘레이션은 무시) | 활발함(0.6.x, 2026년 3월) |
| **oemer** | U-Net 분할 + 규칙 기반 조립 | MIT *(확인 필요)* | 인쇄 악보의 휴대폰 사진 | MusicXML | 개발이 느려짐(마지막 푸시 2025년경) |
| 연구용 엔드투엔드 모델 (TrOMR, SMT/Sheet Music Transformer, Polyphonic-TrOMR 등) | 이미지→시퀀스 트랜스포머 | 다양, 연구 전용인 경우가 많음 | 깨끗하고 잘라낸 단일 시스템 | **kern / 자체 토큰 | 유망하지만 파인튜닝과 엔지니어링이 필요. 바로 쓸 수 있는 상태가 아님. |
| 상용 OMR (PlayScore, ScanScore, SmartScore, Newzik 엔진 등) | 독점 | 상용 / SDK 조건 미확인 *(조사 필요)* | 다양 | MusicXML | 오픈소스가 실패할 때의 대안 |

OMR 공통 한계: 가사가 약하거나 무시됨(homr와 oemer는 대부분 건너뜀), 코드 심볼은 대부분 무시, 한국어 텍스트 미지원, 반복과 점프 처리가 일관되지 않음, 기울어짐·그림자·휜 페이지·저해상도에서 정확도가 급격히 떨어짐.

### D. 하이브리드 (권장)

```
페이지 ─► 전처리 (기울기 보정, 왜곡 보정, 잡음 제거, ~300 dpi 상당으로 업스케일)
       ├─► 레이아웃: 오선 검출 (OMR 엔진 자체) + 텍스트 영역 (OCR)
       ├─► OCR (Vision) ─► 코드 문법 ─► 코드, 라벨, 가사, 제목            [bbox ✓]
       ├─► OMR 엔진 ─► 음표/쉼표/조표/박자/마디선                          [bbox: 엔진에 따라 다름]
       └─► 비전 LLM ─► 이미지 + OCR 토큰 + OMR 마디 요약을 받아서:
                        섹션 구성, 제목/아티스트, 반복 의미, 코드 수정
                        (토큰 ID / 마디 번호를 반드시 인용 — 임의로 지어내기 불가)
                │
                ▼
        ScoreIR로 병합 (각 요소: 값, 페이지, bbox, 마디, 신뢰도, 출처)
                │
                ▼
        검증 (결정적)
          • 마디 음표 길이 합 == 박자표 (못갖춘마디/마지막 마디 제외)
          • 조표 vs. 임시표 빈도 vs. 코드 근음 (Krumhansl 방식 키 프로필)
          • 코드 심볼 문법 + 강박에서 코드와 멜로디 일치 여부 (약한 검사)
          • 시스템별 음표 수 대비 가사 음절 수
          • 반복/볼타 구조가 올바른지
                │
                ▼
        표시 항목 ─► 검토 UI ─► 사용자가 확인한 ScoreIR ─► MusicXML (music21) ─► 렌더링
```

하이브리드를 쓰는 이유: 각 구성요소가 서로의 약점을 보완하고, *그리고* 검증 단계가 구성요소 사이의 불일치를 조용한 오류 대신 검토 대상으로 바꿉니다. 예를 들어 OMR은 D키(♯ 2개)라고 하는데 코드가 전부 E♭ 계열이면, 키가 검토 대상으로 표시됩니다.

## 3. 중간 표현 (ScoreIR)

특정 제공자에 묶이지 않아야 하고, 손실 없이 MusicXML로 변환할 수 있어야 합니다. 초안:

```ts
type Provenance = "ocr" | "omr:audiveris" | "omr:homr" | "llm:<model>" | "rule" | "user";
interface SourceRef { assetId: string; page: number; bbox?: [x, y, w, h] /* 페이지 기준 정규화 0..1 */ }
interface Recognized<T> { value: T; source: SourceRef; confidence: number; provenance: Provenance;
                          alternatives?: { value: T; provenance: Provenance; confidence: number }[];
                          flags?: ValidationFlag[]; reviewed?: boolean }

interface ScoreIR {
  meta: { title?: Recognized<string>; artist?: Recognized<string>; key: Recognized<KeySig>; time: Recognized<TimeSig>; tempo?: Recognized<number> };
  parts: { id: string; name: string; staves: number }[];
  measures: { index: number; source: SourceRef; barline?: ...; repeat?: ...;
              events: Recognized<NoteEvent | RestEvent>[]; harmony: Recognized<ChordSymbol>[];
              lyrics: Recognized<LyricSyllable>[] }[];
  sections: Recognized<{ label: string; startMeasure: number; endMeasure: number }>[];
}
```

`ChordChartDoc`(모드 ①, ②)는 이것의 *코드 전용 부분집합*입니다. 현재의 `Song.sections[].lines[].segments[]`와 `chordPosition`을 `SourceRef`로 일반화한 것입니다. 음높이는 MIDI 번호가 아니라 **표기 그대로**(`step`, `alter`, `octave`) 저장해서, 변환을 거쳐도 표기가 유지됩니다.

## 4. MusicXML 변환과 렌더링

- **쓰기:** 워커에서 music21(BSD) 사용. ScoreIR → `music21.stream.Score` → MusicXML 4.0. 검증 도구(키 분석, 마디 채움 확인)도 함께 얻음.
- **읽기** (사용자가 가져온 MusicXML, 예: MuseScore 내보내기): 서버의 music21, 또는 필요한 부분만 처리하는 기기 내 TS 파서(3단계).
- **렌더링:** OSMD(BSD-3) vs. Verovio(LGPL-3.0). PoC E4에서 비교: 한국어 가사가 있는 리드시트의 조판 품질, 코드 심볼 위치, WebView에서의 메모리와 속도, 전조 표시.
- **MusicXML 전조**는 자체 TS 엔진에서 처리(`<key><fifths>`, `<pitch>` step/alter/octave, `<harmony>` root/bass, 이조 악기용 `<transpose>`). music21의 `transpose()`는 **테스트 기준값으로만** 사용.

## 5. 예상되는 한계 (제품에서 솔직하게 알릴 것)

1. 비스듬히 찍거나 어두운 곳에서 찍은 사진은 PDF보다 수정이 더 필요함. 인식 전에 품질 점수를 보여주고 다시 찍기를 권장.
2. 손으로 쓴 기보: 범위 밖. 인쇄 악보 위에 손으로 쓴 *코드*: 최선을 다하되 항상 검토 대상으로 표시.
3. 피아노/SATB 다중 오선 악보: 정확도가 낮음. MVP의 모드 ③은 **단일 오선 리드시트**(멜로디 + 코드 + 가사)를 대상으로 하며, 이는 한국 CCM에서 가장 흔한 형식이기도 함.
4. 복잡한 점프 구조(볼타가 있는 D.S. al Coda): 기호로는 인식하지만, 흐름 해석은 사용자가 Song Flow에서 확정.
5. 인식 결과는 언제나 초안. 검토하지 않은 악보는 볼 수는 있지만 팀에 배포할 수는 없음.

## 7. 권장안

1. **모드 ①/②는 접근법 A에 D의 LLM 단계를 더해 출시.** LLM은 라벨과 제목에만 사용. 코드 F1을 비용을 정당화할 만큼 올리는지 측정.
2. **PoC 진행**: homr와 Audiveris를 나란히(oemer는 세 번째로). 두 AGPL 엔진 모두 수정하지 않고, 격리된 서버 프로세스로 실행.
3. **모드 ③ 진행 여부는 원시 정확도가 아니라 수정 시간으로 결정.**
4. **제공자는 교체 가능하게 유지**: `OcrProvider`, `VisionLlmProvider`, `OmrEngine` 인터페이스. 모든 요소에 출처를 기록해서, 나중에 실제 사용자 데이터(동의 하에)로 엔진을 비교할 수 있게 함.
